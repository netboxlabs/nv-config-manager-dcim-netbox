The `netbox` DCIM provider translates NetBox records into the provider-neutral
`RenderData` contract before the Render service or a template filter sees them.
Templates use the fields and filters documented here; they never query NetBox or
read `config_context` directly.

It doubles as a coverage checklist: a filter marked **not yet populated**
consumes a `RenderData` section this provider currently returns as the SDK
default, and is an untested provider boundary.

## BGP peering

NetBox models BGP through the `netbox-bgp` plugin. Each peering is a `session`
with nested `local_as`, `remote_as`, `local_address`, `remote_address`, and
`peer_group`. A `netbox-bgp` session does **not** expose a VRF association, so the
provider does not require or emit a `source_interface`, and
`RenderBGPPeer.source_vrf` is the default VRF.

Sessions are grouped into one `RenderBGPInstance` per local ASN. Instances with
no peers are still returned. `router_id_interface` is not exposed by
`netbox-bgp` and is currently unset.

## Device filter mapping

The "NetBox source" column describes the provider implementation. GraphQL is used
for the device, its interfaces, and merged `config_context`; REST is used for the
`netbox-bgp`, overlay/VXLAN, and IPAM relationships.

The `services`, `firmware`, `access`, and routing ASN/EVPN/ISIS sections read the
same canonical `config_context` keys the fabric templates expect (the keys the
bundled `config_contexts.yaml` seeds). NetBox merges region/site/role/platform/tag
config contexts into `device.config_context`, so a device gets its effective
policy; where a key is absent the section stays at the SDK default.

### Not yet populated (SDK default)

One section is still returned as the SDK default:

| Filter(s) | Section | Note |
| --- | --- | --- |
| — | `plugin_data` | An SDK extension point for provider-specific data. The reference provider does not populate it either. |

Everything else the filters read is now mapped. The ones that took the most
work to source:

| Section | NetBox source |
| --- | --- |
| `network.console_server_ports[]` | Native `consoleserverports` and their connected console port |
| `network.nvlink_topology` | The plugin's NVLink domain for the device |
| `routing.bgp_instances[].router_id_interface` | The device's loopback interface |
| `routing.bgp_instances[].peers[].ttl` | `netbox-bgp` `extra_attributes.ttl`, on the session or its peer group |
| `overlays.l2_vni_vrfs[]` | Device-level overlay assignments, with route targets from the VXLAN or the assignment |
| `location.topology.route_servers[]` | Devices at the site tagged `route-server` |
| `location.topology.wan_routers[]` | Devices at the site with the `WAN` or `TAN-BBR` role |
| `interfaces[].connected_interface` | Cable connected-endpoint data |
| `interfaces[].member_interfaces` | Inverted LAG membership |
| `address_space.vlans[].helper_addresses` | The `nvcm_helper_addresses` VLAN custom field |

## Known filter requirements

- **VRF route distinguisher.** `attached_vrfs` / `has_vrf` / `get_vrf` build a
  template `VRF` via the shared library's `VRF.from_render_data`, which requires
  the route distinguisher in the overlay form `*:<vni>` (what NVCM's fabric VRFs
  use, e.g. `*:60000`). A conventional `ASN:index` RD raises
  `FilterException: Invalid RD set on VRF <name>`. Ensure interface VRFs carry an
  `*:<vni>` RD, or the VRF filters will fail.

## Location filter mapping

| Filter | Provider-neutral input | NetBox source |
| --- | --- | --- |
| `site_aggregates` | `address_space.prefixes[]` | IPAM prefixes scoped to the site, with role and tags |
| `location_has_tag` | `location.tags` | **not yet populated** — the Site `RenderLocation` does not yet carry tags |

## IP utility filters

`gateway`, `subnet`, `supernet`, `get_peer_ip`, `network_address`, and
`host_range` operate only on the value passed to the filter. They do not consume
a `RenderData` field or query NetBox.
