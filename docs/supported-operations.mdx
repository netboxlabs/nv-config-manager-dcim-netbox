The `netbox` provider implements the **entire** `DCIMClient` protocol (73
operations) against native NetBox REST and GraphQL — there are **no**
`DCIMOperationNotSupportedError` stubs. This page catalogs the operation surface
and the NetBox-specific semantics an integrator needs to know; for the
render-data field mapping see [NetBox data mapping](./netbox-data-mapping.mdx).

## Operation surface

| Group | Operations | NetBox note |
| --- | --- | --- |
| **Lifecycle / transport** (2) | `close`, `get_device_ui_url` | UI URL uses `public_url`. |
| **Device inventory & selection** (10) | `get_device_metadata`, `get_managed_device_metadata`, `get_device_serial`, `get_device_selection_by_name`, `list_devices`, `get_device_interfaces`, `get_network_device`, `get_network_devices`, `get_host_device`, `get_host_devices` | `list_devices` returns only devices with a **primary IP**. |
| **Reference lookups** (6) | `list_locations`, `list_tenants`, `list_roles`, `list_namespace_tags`, `list_overlays`, `list_statuses` | `list_statuses` reads OPTIONS choices; namespaces are VRF tags. |
| **Render** (2) | `get_render_data`, `get_intended_interface_neighbors` | Returns the provider-neutral `RenderData`; portable REST + one GraphQL query. |
| **Config lifecycle / state** (9) | `get_render_device_status`, `get_render_enabled_device_ids`, `get_render_template_versions`, `upsert_intended_configuration`, `update_render_template_version`, `get_backup_enabled_device_ids`, `get_configuration_backup_metadata`, `record_configuration_backup`, `has_recorded_config_drift` | Backed by the plugin's `DeviceConfigStatus` / `IntendedConfig` / `BackupConfig` models, not device custom fields. |
| **DHCP** (4) | `get_dhcp_site_options`, `get_dhcp_contexts`, `get_dhcp_static_data`, `get_dhcp_auto_subnets` | **Read-only** (generates Kea config); does not write DCIM. |
| **ZTP** (2) | `get_ztp_device`, `mark_ztp_device_provisioned` | Writes NetBox device status `provisioned` — an extra choice the companion plugin registers (see below). |
| **Firmware** (4) | `get_os_image_versions`, `set_intended_os_image`, `get_firmware_bundle`, `set_device_firmware_intent` | Sourced from the merged `config_context`. |
| **Hosts / MAC correlation** (6) | `find_host_devices_by_mac`, `update_dpu_device_inventory`, `get_interface_hosts_by_mac`, `get_host_metadata_by_macs`, `get_host_metadata_by_names`, `get_connected_switch_port_by_remote_mac` | MAC is a first-class `MACAddress` object. |
| **Secrets** (3) | `get_device_password_mapping_users`, `get_device_secret_versions`, `get_device_password_secret_names` | Returns secret **references** from `config_context`; no secret store. |
| **IPAM / VRF** (4) | `get_device_vrfs`, `assign_vrf_to_device`, `assign_vrf_to_interface`, `get_namespace_route_distinguishers` | `assign_vrf_to_device` / `remove_unmapped_device_vrfs` are no-ops: the ports stage is the association. |
| **Spectrum-X overlays** (5) | `get_spectrum_x_vrfs`, `provision_spectrum_x_vrf`, `delete_spectrum_x_vrf`, `delete_spectrum_x_overlay_if_unused`, `reconcile_spectrum_x_overlay_assignments` | One VRF per tenant (no NetBox Namespace); overlays live in the fabric plugin. |
| **InfiniBand** (16) | `get_ib_switch_topology`, `get_ib_interface_guid(s)`, `set_ib_interface_guid`, `get_ib_interface_records`, `find_ib_interfaces_by_guids`, `ensure_ib_pkey_partition`, `ensure_orphan_ib_pkey`, `cleanup_ib_pkey_partition`, `ensure_ib_pkey_assignments`, `remove_ib_pkey_assignments`, `get_ib_pkey_assignments`, `sync_ib_pkey_assignments`, `canonicalize_ib_host`, `resolve_ib_host_site`, `resolve_ib_pkey_context` | PKeys/partitions are plugin models; hosts resolve by name or primary IPv4. |

Provider-lifecycle methods (outside `DCIMClient`): `validate_settings`,
`create_client`, `normalize_event`, `register_render_event_handlers`.

## NetBox-specific semantics

Because NetBox and Nautobot model DCIM differently, several operations map to a
NetBox-native concept rather than a 1:1 equivalent:

- **IPAM namespace = VRF.** NetBox has no first-class `Namespace`; a namespace
  (an isolated zone of unique IP space) is modeled as a **VRF**. A namespace
  *zone* is a set of VRFs sharing a `namespace_tag`; `list_namespace_tags` /
  `get_namespace_route_distinguishers` operate on that tag.
- **No device↔VRF link.** VRFs attach to interfaces/prefixes/IPs, never to
  devices, so `assign_vrf_to_device` and `remove_unmapped_device_vrfs` change
  nothing; the ports stage assigns the selected interfaces and `get_device_vrfs`
  reads the union of their VRFs back. Setting the VRF on every interface would
  move other tenants' ports on a shared switch.
- **Statuses** are per-model **choice fields**, not `Status` objects.
  `list_statuses` reads them from the endpoint's `OPTIONS` response
  (`actions.POST.status.choices`) and returns the status **value** (e.g.
  `active`), which round-trips into `?status=` filters. Whatever choices a model
  actually offers are what you get — including any the companion plugin adds via
  `FIELD_CHOICES` (this is how `mark_ztp_device_provisioned` can write
  `provisioned`), and including model-specific sets such as `dcim.cable`'s
  `connected`. A content type with no status field, or an unknown one, raises
  `DCIMInvalidDataError` rather than returning an empty list.
- **MAC = `MACAddress` model.** NetBox 4.x has no scalar `interface.mac_address`;
  MACs are `MACAddress` objects with the interface's `primary_mac_address`
  pointing at one. `update_dpu_device_inventory` upserts them.
- **Secrets are references.** The secret operations return *which* secret / *which*
  version (from `config_context`), never secret material. NetBox is not the secret
  store, and `netbox-secrets` is not required.
- **`list_devices` requires a primary IP.** Devices without a primary IP are
  intentionally excluded from selection (faithful to the reference).
- **BGP via `netbox-bgp`, REST only.** The plugin exposes no GraphQL, so BGP is
  read over REST (`plugins/bgp/session/`); a session has no VRF association.
- **"Site" is a NetBox Location name.** Overlay/Spectrum-X operations key on
  `dcim.Location` (the `Overlay.location` FK); a NetBox *Site* name resolves only
  if a Location of that name exists.
- **Interface `role`** has no native NetBox field; it is read from the
  `nvcm_interface_role` custom field, which the render and DHCP paths both use to
  gate per-role behaviour (uplink/downlink templates, per-role DHCP options).
- **Cabling requires both ends.** A `connected_interface` to a device that isn't
  modeled in NetBox cannot form a cable, so those far-ends are not populated
  (a NetBox data-model difference, not a data error).
